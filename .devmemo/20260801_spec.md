# vem (Virtual Environments Manager) Specification

## 1. Overview

`vem` is a CLI tool that manages the actual contents of Python virtual environments in a centralized per-user directory and creates directory links to those virtual environments at arbitrary locations.

The actual virtual environments are stored at fixed locations under the `house`. At locations specified by the user, such as project directories, a symbolic link or Windows junction is created that references the actual virtual environment.

After creation, the actual virtual environment is never moved. The `move` command moves only the link.

---

## 2. Objectives

`vem` solves the following problems:

* Separate actual virtual environments from project directories
* Allow multiple links to be created for a single virtual environment
* Centrally manage virtual environment storage locations
* Record the correspondence between virtual environments and links
* Detect inconsistencies such as broken links or missing virtual environments
* Provide the same CLI operations on Windows and POSIX systems wherever possible
* Store management data in a human-readable JSON format

---

## 3. Non-Objectives

The following are out of scope for the initial specification:

* Moving an actual virtual environment to another house
* Moving the house itself
* Sharing virtual environments across multiple machines
* Cloning virtual environments
* Synchronizing Python packages
* Dependency management using `requirements.txt` or similar files
* Project management features provided by Poetry, Pipenv, uv, or similar tools
* Automatic installation of Python versions
* A house stored on remote storage
* Guaranteed operation on network file systems
* Automatic registration of unmanaged links
* Automatic repair of a broken virtual environment itself

---

## 4. Terminology

### 4.1 house

The root directory used to store actual virtual environments, management data, lock files, and temporary files.

### 4.2 environment

The actual Python virtual environment stored in the `house`, together with the management information associated with that virtual environment.

### 4.3 environment ID

A UUID that uniquely identifies a virtual environment.

UUID version 4 is used, and UUIDs are stored and displayed in the standard lowercase hyphen-separated format.

Example:

```text
7bc574b2-1684-4fc6-995a-a7629e216f03
```

### 4.4 name

A user-defined identifier for a virtual environment.

A name must be unique within the same house.

### 4.5 link

A directory link created at a user-specified location that points to the actual virtual environment.

On POSIX systems, a symbolic link is used.

On Windows, a junction is used by default, with symbolic links also available as an option.

### 4.6 metadata

Management information belonging to an individual environment.

It is stored in `metadata.json` within each environment directory.

### 4.7 registry

Index information used to locate environments within the house.

It is stored in `registry.json`.

The registry is a rebuildable index. The authoritative management information for each environment is stored in `metadata.json`.

---

## 5. House Location

### 5.1 Default Values

The default house location is determined from the user-specific application data directory for each operating system.

#### Linux and Other Unix Systems

```text
${XDG_DATA_HOME:-$HOME/.local/share}/vem
```

If `XDG_DATA_HOME` is unset or empty, the following is used:

```text
$HOME/.local/share/vem
```

#### macOS

```text
$HOME/Library/Application Support/vem
```

#### Windows

```text
%LOCALAPPDATA%\vem
```

`%APPDATA%` is not used. Virtual environments contain machine-specific data and therefore must not be treated as roaming data.

### 5.2 House Resolution Priority

The house is determined using the following priority order:

1. The `--house` command-line option
2. The `VEM_HOUSE` environment variable
3. The operating-system-specific default value

### 5.3 House Path Normalization

The following processing is applied to the specified house path:

* Expand user home directory notation
* Expand environment variables
* Convert to an absolute path
* Normalize `.` and `..`
* Remove unnecessary trailing path separators

On Windows, path comparisons are case-insensitive.

### 5.4 House Constraints

* The house is assumed to be located on a local file system
* The house must not be moved after it has been created
* The absolute house path must not be changed after a virtual environment has been created
* Different houses are treated as mutually independent management domains
* Names, UUIDs, and link information are not shared between different houses
* Changing `--house` does not automatically move existing environments

---

## 6. House Directory Structure

```text
<house>/
├── registry.json
├── environments/
│   └── <UUID>/
│       ├── metadata.json
│       └── venv/
├── lock
└── tmp/
```

### 6.1 registry.json

An index used to locate environments within the house.

### 6.2 environments

Contains one management directory per environment.

### 6.3 metadata.json

Contains the authoritative management information for an environment.

### 6.4 venv

The actual Python virtual environment.

The actual environment path has the following form:

```text
<house>/environments/<UUID>/venv
```

### 6.5 lock

A lock used to provide exclusive access for operations that modify the house.

### 6.6 tmp

Used for environments that are still being created and for other temporary processing.

Temporary files used for atomic replacement of management JSON files should, in principle, be created in the same directory as the JSON file being replaced.

---

## 7. Basic Management Data Policy

### 7.1 Authoritative Sources

Information is classified as follows:

1. `metadata.json`

   * The authoritative management information for an environment
2. The actual file system

   * The current state of actual environments and links
3. `registry.json`

   * A rebuildable index that assists searches by name or UUID

### 7.2 Registry Reconstruction

If `registry.json` is lost or corrupted, it must be possible to reconstruct it by scanning:

```text
<house>/environments/*/metadata.json
```

### 7.3 Manual Editing

JSON files are human-readable internal management files.

Manual editing is not officially supported.

As a rule, management information should be modified using `vem` commands.

---

## 8. registry.json

### 8.1 Purpose

`registry.json` is an index for locating environments by environment ID and name.

It does not store link lists or detailed Python information. Each `metadata.json` file is the authoritative source for that information.

### 8.2 Format

```json
{
  "schema_version": 1,
  "revision": 12,
  "updated_at": "2026-08-01T10:30:00+09:00",
  "environments": {
    "7bc574b2-1684-4fc6-995a-a7629e216f03": {
      "name": "project-a",
      "metadata_path": "environments/7bc574b2-1684-4fc6-995a-a7629e216f03/metadata.json"
    },
    "196b5579-5f84-4f60-a5ea-f9e02db7e72c": {
      "name": null,
      "metadata_path": "environments/196b5579-5f84-4f60-a5ea-f9e02db7e72c/metadata.json"
    }
  }
}
```

### 8.3 Fields

#### `schema_version`

The version of the JSON schema.

It must be an integer.

#### `revision`

A non-negative integer incremented on each registry update.

#### `updated_at`

The date and time when the registry was last updated successfully.

It must be a timezone-aware RFC 3339 date-time string.

#### `environments`

A JSON object keyed by environment ID.

#### `name`

The environment name.

If no name is assigned, the value is `null`.

#### `metadata_path`

A path relative to the house.

Absolute paths must not be stored.

### 8.4 Registry Constraints

* Environment IDs must be unique
* `name` must be either `null` or a string
* Names must be unique within the same house
* Name duplicate detection is case-insensitive
* `metadata_path` must be relative to the house
* `metadata_path` must not point outside the house

---

## 9. metadata.json

### 9.1 Purpose

Stores the authoritative management information for an individual environment.

### 9.2 Format

```json
{
  "schema_version": 1,
  "revision": 8,
  "id": "7bc574b2-1684-4fc6-995a-a7629e216f03",
  "name": "project-a",
  "state": "ok",
  "created_at": "2026-08-01T10:00:00+09:00",
  "updated_at": "2026-08-01T10:30:00+09:00",
  "last_error": null,
  "python": {
    "requested_executable": "/usr/bin/python3.13",
    "base_executable": "/usr/bin/python3.13",
    "version": "3.13.5"
  },
  "venv": {
    "path": "venv"
  },
  "links": [
    {
      "path": "/home/user/projects/project-a/.venv",
      "type": "symlink",
      "created_at": "2026-08-01T10:00:10+09:00",
      "updated_at": "2026-08-01T10:00:10+09:00"
    }
  ]
}
```

### 9.3 Fields

#### `schema_version`

The metadata schema version.

#### `revision`

A non-negative integer incremented on each metadata update.

#### `id`

The environment ID.

It must match the UUID used as the parent directory name.

#### `name`

The environment name.

If no name is assigned, the value is `null`.

#### `state`

The management state of the environment.

#### `created_at`

The date and time when environment creation began.

#### `updated_at`

The date and time when the metadata was last updated successfully.

#### `last_error`

The last recorded critical error.

If there is no error, the value is `null`.

Sensitive information and complete environment variable sets must not be stored.

#### `python.requested_executable`

The Python executable specified using `create --python`.

If omitted, this is the Python executable used to run `vem`.

#### `python.base_executable`

The base Python executable identified from the virtual environment after creation.

`null` is allowed if it cannot be obtained.

#### `python.version`

The Python version of the virtual environment.

`null` is allowed if it cannot be obtained.

#### `venv.path`

A path relative to the environment management directory that points to the actual virtual environment.

In the initial schema, it is always:

```json
"venv"
```

#### `links`

An array of registered links.

### 9.4 Link Object

#### `path`

The absolute path of the link itself.

This is not the resolved target path.

#### `type`

One of the following:

```text
symlink
junction
```

#### `created_at`

The date and time when the link was first registered.

#### `updated_at`

The date and time when the link information was last updated.

## 10. JSON Representation Rules

### 10.1 Character Encoding

UTF-8 must be used.

A BOM must not be included.

### 10.2 Line Endings

New files must use LF line endings regardless of the operating system.

### 10.3 Formatting

* Use two spaces for indentation
* Prefer the key order defined by the specification
* Include a newline at the end of the file
* Do not unnecessarily escape non-ASCII characters in JSON output
* Do not output values that do not exist in standard JSON, such as `NaN` or `Infinity`
* Do not use trailing commas
* Do not use comments

### 10.4 Date and Time

Dates and times are stored in RFC 3339 format.

Example:

```text
2026-08-01T10:30:00+09:00
```

Include the local timezone offset wherever possible.

Date-time values may be normalized to UTC for comparison.

---

## 11. Path Storage and Comparison

### 11.1 Link Paths

Link paths are stored as absolute paths after applying the following processing:

* Expand `~`
* Expand environment variables
* Resolve relative paths against the current working directory
* Normalize `.` and `..`
* Remove unnecessary trailing separators

The link path itself must not be resolved as a symbolic link.

### 11.2 Paths Within the House

Managed paths within the house should be stored in JSON as paths relative to the house wherever possible.

### 11.3 Path Comparison

On POSIX systems, comparisons are case-sensitive in principle.

On Windows, comparisons are case-insensitive.

On Windows, drive letters, path separators, and other comparison-related path forms must be normalized.

### 11.4 Uniqueness

Multiple representations of the same path must not be registered as duplicate links.

---

## 12. Name Specification

### 12.1 Optionality

A name is optional.

An environment without a name is referenced by ID.

### 12.2 Uniqueness

A name must be unique within the same house.

Duplicate detection is case-insensitive.

For example, the following are duplicates:

```text
project-a
Project-A
PROJECT-A
```

### 12.3 Allowed Characters

A name may contain:

* Unicode characters
* Alphanumeric characters
* Hyphens
* Underscores
* Periods

However, the following are prohibited:

* `/`
* `\`
* NUL characters
* Control characters
* `.` by itself
* `..` by itself
* Leading or trailing whitespace
* An empty string

The maximum name length is 255 Unicode code points.

## 13. CLI Format

```text
vem [GLOBAL_OPTIONS] COMMAND [COMMAND_OPTIONS] [ARGUMENTS]
```

---

## 14. Global Options

### 14.1 `--house PATH`

Specifies the house to use.

```text
vem --house PATH COMMAND
```

### 14.2 `--version`

Displays version information and exits.

### 14.3 `-h`, `--help`

Displays help and exits.

### 14.4 `--no-color`

Disables colorized terminal output.

JSON output is never colorized.

---

## 15. Link Types

Commands that create links may use the following option:

```text
--link-type auto|junction|symlink
```

### 15.1 `auto`

The default value.

* Windows: junction
* POSIX: symlink

### 15.2 `junction`

Creates a Windows junction.

Specifying this option on a non-Windows system is an argument error.

### 15.3 `symlink`

Creates a directory symbolic link.

On Windows, an error is returned if the link cannot be created because of insufficient privileges or operating-system settings.

If the user explicitly specifies `symlink`, the command must not silently fall back to a junction.

# 16. create Command

## 16.1 Overview

Creates a new Python virtual environment inside the house and creates a link at a user-specified location.

## 16.2 Syntax

```text
vem [--house PATH] create
    [--name NAME]
    [--python PYTHON]
    [--link-type auto|junction|symlink]
    LINK_PATH
```

## 16.3 Arguments

### `LINK_PATH`

The path at which to create a link to the new virtual environment.

A relative path is converted to an absolute path using the current working directory.

### 16.4 Options

#### `--name NAME`

Assigns a name to the environment.

#### `--python PYTHON`

Specifies the Python executable used to create the virtual environment.

If omitted, the Python interpreter running `vem` is used.

#### `--link-type TYPE`

Specifies the type of link to create.

## 16.5 Preconditions

* The name is valid
* The name is not already in use
* The specified Python executable exists
* The specified Python executable can be executed
* The `venv` module is available in the specified Python installation
* `LINK_PATH` does not exist
* The parent directory of `LINK_PATH` exists
* The house is writable
* The house lock can be acquired

The parent directory is not created automatically.

## 16.6 Environment ID

Generate a UUID version 4.

Check for collisions with existing environment IDs.

## 16.7 Processing

1. Determine and normalize the house
2. Acquire the exclusive house lock
3. Validate the registry and existing metadata
4. Validate the name, Python executable, and `LINK_PATH`
5. Generate an environment ID
6. Create a temporary environment directory
7. Create initial metadata with `state: "creating"`
8. Create the virtual environment using processing equivalent to the following command:

```text
PYTHON -m venv TEMPORARY_VENV_PATH
```

9. Run the virtual environment’s Python executable and verify its version and other information
10. Move the environment directory to its final UUID path
11. Create the link at `LINK_PATH`
12. Verify that the link target matches the actual virtual environment
13. Register the link information in the metadata
14. Change the metadata state to `ok`
15. Add the environment index entry to the registry
16. Save the registry and metadata atomically
17. Release the house lock

The final actual virtual environment path is:

```text
<house>/environments/<UUID>/venv
```

## 16.8 Success Conditions

The operation succeeds only if all of the following conditions are satisfied:

* The actual virtual environment exists
* The Python executable inside the virtual environment can be run
* The link exists
* The link target matches the actual virtual environment
* The metadata has been saved successfully
* The environment is registered in the registry

## 16.9 Failure Handling

If an operation fails partway through, attempt to roll back the following wherever possible:

* Delete any created link
* Delete the partially created actual virtual environment
* Delete the environment management directory
* Remove the registry entry

If rollback cannot be completed, leave any remaining metadata in the `broken` state and record a summary in `last_error`.

---

# 17. link Command

## 17.1 Overview

Creates a new link to an existing managed environment.

## 17.2 Syntax

```text
vem [--house PATH] link
    (--name NAME | --id UUID)
    [--link-type auto|junction|symlink]
    LINK_PATH
```

## 17.3 Target Selection

Exactly one of the following must be specified:

```text
--name NAME
--id UUID
```

They must not be specified together.

## 17.4 Preconditions

* The target environment exists
* The metadata can be read
* The actual environment exists
* The environment state permits link creation
* `LINK_PATH` does not exist
* The parent directory of `LINK_PATH` exists
* The same link path is not already registered

Links may be added to environments in the `ok` or `orphan` state.

As a rule, link creation must be rejected for environments in the `creating`, `missing-environment`, or `broken` state.

## 17.5 Processing

1. Acquire the house lock
2. Locate the target environment in the registry
3. Validate the metadata and actual environment
4. Validate `LINK_PATH` and the link type
5. Create the link
6. Validate the link target
7. Add the link information to the metadata
8. Change the state to `ok`
9. Save the metadata atomically
10. Release the house lock

## 17.6 Failure Handling

If validation after link creation or metadata persistence fails, attempt to delete the created link.

If the link cannot be deleted, record the actual link in the metadata wherever possible and set the environment state to `broken`.

---

# 18. move Command

## 18.1 Overview

Moves a managed link to another location.

The actual virtual environment is not moved.

## 18.2 Syntax

```text
vem [--house PATH] move SOURCE_LINK DESTINATION_LINK
```

## 18.3 Arguments

### `SOURCE_LINK`

The managed link to move.

### `DESTINATION_LINK`

The destination link path.

## 18.4 Preconditions

* `SOURCE_LINK` is registered in metadata
* `SOURCE_LINK` actually exists as a link
* The type of `SOURCE_LINK` matches the registered type
* `SOURCE_LINK` references the registered actual environment
* `DESTINATION_LINK` does not exist
* The parent directory of `DESTINATION_LINK` exists
* `SOURCE_LINK` and `DESTINATION_LINK` are not the same path

## 18.5 Processing

1. Acquire the house lock
2. Search all metadata or an index for `SOURCE_LINK`
3. Validate the source link type and target
4. Confirm that `DESTINATION_LINK` is available
5. Create a new link of the same type as the source link
6. Validate the new link target
7. Delete the source link
8. Update the link path in the metadata
9. Save the metadata atomically
10. Release the house lock

The source link must not be deleted until creation and validation of the new link are complete.

## 18.6 Failure Handling

### Failure Before or During New Link Creation

Do not modify the source link.

### Failure After New Link Creation but Before Source Link Deletion

Delete the new link and attempt to restore the original state.

### Source Link Deletion Failure

Register both the old and new links in the metadata and set the environment state to `broken`.

### Metadata Persistence Failure

Reinspect the file system.

If recovery is not possible, the inconsistency must be detected by the next `doctor` or `status` operation.

---

# 19. unlink Command

## 19.1 Overview

Deletes the specified managed link and removes its link information from the metadata.

By default, the actual environment is not deleted.

## 19.2 Syntax

```text
vem [--house PATH] unlink
    [--delete-if-orphan]
    LINK_PATH
```

## 19.3 Options

### `--delete-if-orphan`

If no registered links remain for the environment after deleting the link, also delete the actual environment and its management information.

## 19.4 Pre-Deletion Validation

The link is deleted only if all of the following conditions are satisfied:

* `LINK_PATH` is registered in metadata
* `LINK_PATH` actually exists
* `LINK_PATH` is not a regular file or regular directory
* `LINK_PATH` is a symlink or junction
* The link type matches the metadata
* The link target matches the registered actual environment

If validation fails, the link must not be deleted.

## 19.5 Processing

1. Acquire the house lock
2. Locate the environment associated with `LINK_PATH`
3. Validate the link
4. Delete the link
5. Remove the link information from the metadata
6. Check the number of remaining links
7. If links remain, set the state to `ok`
8. If no links remain, set the state to `orphan`
9. Save the metadata atomically
10. If `--delete-if-orphan` is specified, delete the environment
11. Release the house lock

An API that recursively deletes the link target must not be used to delete the link.

## 19.6 If the Link No Longer Exists

If the link is registered in the registry or metadata but does not exist, a normal `unlink` operation returns an error.

This inconsistency is handled by `doctor` or a future `unlink --forget` option.

---

# 20. remove Command

## 20.1 Overview

Deletes the actual virtual environment and management information for a managed environment.

## 20.2 Syntax

```text
vem [--house PATH] remove
    (--name NAME | --id UUID)
    [--force]
```

## 20.3 Normal Behavior

If the target environment has registered links, return an error.

Deletion is performed only when there are no links.

## 20.4 `--force`

Validates and deletes all registered links before deleting the environment.

## 20.5 Pre-Deletion Validation

* The target environment ID is valid
* The environment management directory is under the house
* The environment management directory name matches the metadata ID
* The actual venv path is under the environment management directory
* `venv.path` does not contain path traversal
* If registered links exist, each one references the target environment

Even when `--force` is specified, links that cannot be validated must not be deleted unconditionally.

## 20.6 Processing

1. Acquire the house lock
2. Locate the target environment
3. Validate the metadata, actual environment, and links
4. If `--force` is specified, delete the registered links
5. Delete the environment management directory
6. Remove the environment from the registry
7. Save the registry atomically
8. Release the house lock

## 20.7 Failure During Deletion

If deletion fails after part of the environment directory has been removed, change any remaining metadata to the `broken` state if possible.

If the environment has been completely deleted and no metadata remains, remove the corresponding registry entry and emit a warning.

---

# 21. status Command

## 21.1 Overview

Displays the state of managed environments and links.

As a rule, `status` does not modify management data.

## 21.2 Syntax

```text
vem [--house PATH] status
    [--name NAME | --id UUID | --path LINK_PATH]
    [--json]
```

## 21.3 Filters

The following options are mutually exclusive:

```text
--name NAME
--id UUID
--path LINK_PATH
```

If no filter is specified, all environments are displayed.

## 21.4 Displayed Fields

For each environment, display:

* ID
* Name
* Management state
* Actual virtual environment path
* Whether the actual environment exists
* Python executable
* Python version
* Creation date and time
* Update date and time
* Number of registered links
* Metadata revision

For each link, display:

* Link path
* Registered link type
* Actual link type
* Whether the link exists
* Actual link target
* Expected link target
* Link state

## 21.5 Environment States

### `ok`

All of the following are true:

* The metadata is valid
* The actual venv exists
* No registered link has a critical inconsistency
* At least one link is registered

### `orphan`

The actual venv exists, but no links are registered.

### `creating`

Creation has not been completed.

### `missing-environment`

The metadata exists, but the actual venv does not.

### `broken`

The management information or operation state has a critical inconsistency.

### `unknown`

The state value is unknown, or the schema cannot be interpreted correctly.

## 21.6 Link States

### `ok`

The link exists and references the expected actual environment.

### `stale-link`

The link is registered in metadata but does not exist.

### `wrong-target`

The link exists but references a different location.

### `not-a-link`

A regular file or regular directory exists at the registered path.

### `wrong-type`

The target is correct, but the actual link type differs from the registered type.

### `unreadable`

The state cannot be determined because of insufficient privileges or another access failure.

## 21.7 `--json`

Outputs machine-processable JSON to standard output.

Example:

```json
{
  "schema_version": 1,
  "house": "/home/user/.local/share/vem",
  "environments": [
    {
      "id": "7bc574b2-1684-4fc6-995a-a7629e216f03",
      "name": "project-a",
      "state": "ok",
      "metadata_state": "ok",
      "venv_path": "/home/user/.local/share/vem/environments/7bc574b2-1684-4fc6-995a-a7629e216f03/venv",
      "venv_exists": true,
      "python": {
        "executable": "/usr/bin/python3.13",
        "version": "3.13.5"
      },
      "links": [
        {
          "path": "/home/user/projects/project-a/.venv",
          "registered_type": "symlink",
          "actual_type": "symlink",
          "state": "ok",
          "expected_target": "/home/user/.local/share/vem/environments/7bc574b2-1684-4fc6-995a-a7629e216f03/venv",
          "actual_target": "/home/user/.local/share/vem/environments/7bc574b2-1684-4fc6-995a-a7629e216f03/venv"
        }
      ]
    }
  ]
}
```

In JSON mode, human-readable explanatory text must not be mixed into standard output.

Warnings are written to standard error.

# 22. doctor Command

## 22.1 Overview

Checks the house, registry, metadata, actual venvs, and links for inconsistencies.

The initial release must include inspection functionality. Automatic repair functionality may be limited or omitted.

## 22.2 Syntax

```text
vem [--house PATH] doctor
    [--json]
    [--rebuild-registry]
```

## 22.3 Inspection Items

* JSON syntax of `registry.json`
* Registry schema version
* Validity of `metadata_path`
* Match between environment IDs and directory names
* JSON syntax of `metadata.json`
* Metadata schema version
* Match between metadata IDs and directory names
* Duplicate names
* Existence of actual venvs
* Duplicate link paths
* Existence of links
* Link types
* Match between link targets and expected targets
* Managed paths pointing outside the house
* Remaining temporary files or partially created environments
* Environments not present in the registry
* Registry entries whose metadata is missing

## 22.4 `--rebuild-registry`

Scans `environments/*/metadata.json` and rebuilds the registry.

Before rebuilding, validate:

* Metadata JSON syntax
* Environment IDs
* Name uniqueness
* Safety of `metadata_path`

If duplicate names are found, do not resolve them automatically. Fail the reconstruction.

# 23. Atomic JSON File Updates

## 23.1 Basic Principle

An existing JSON file must not be truncated and overwritten directly.

## 23.2 Update Procedure

1. Acquire the house lock
2. Read the current JSON
3. Validate the schema and revision
4. Apply updates in memory
5. Increment the revision by 1
6. Set the update timestamp
7. Create a temporary file in the same directory as the target JSON file
8. Write the complete JSON to the temporary file
9. Flush the buffer
10. Synchronize the file on operating systems that support it
11. Atomically replace the target file with the temporary file
12. Synchronize the parent directory if necessary
13. Release the house lock

## 23.3 Temporary File Names

Examples:

```text
.metadata.json.<random>.tmp
.registry.json.<random>.tmp
```

It should be possible to infer the original file name from the temporary file name.

## 23.4 Backups

Persistent backups for every update are not required in the initial implementation.

The following may be added in the future:

```text
registry.json.bak
metadata.json.bak
```

Even if backups are introduced, they must not be treated as authoritative sources.

---

# 24. Updating Multiple JSON Files

## 24.1 Full Transaction Limitations

Multiple JSON files, links, and actual venvs on a file system cannot be updated as one fully atomic transaction.

## 24.2 Update Order

For operations that create new resources, the order should generally be:

1. Create metadata representing an intermediate state
2. Create the file-system resources
3. Validate the resources
4. Save the final metadata
5. Update the registry

For deletion operations, the order in which the registry and metadata are updated must be explicitly defined according to the target.

## 24.3 Registry Inconsistency

Even if the registry update fails after metadata has been updated, the metadata remains the authoritative source.

In this case, emit a warning and allow recovery using `doctor --rebuild-registry`.

---

# 25. Exclusive Access Control

## 25.1 Applicable Commands

The following commands acquire an exclusive house-level lock:

* `create`
* `link`
* `move`
* `unlink`
* `remove`
* `doctor --rebuild-registry`

## 25.2 Read-Only Commands

As a rule, `status` and a normal `doctor` operation use a shared lock or a short-lived read lock.

If cross-platform shared locking is difficult, a short-lived exclusive lock or a consistency revalidation approach may be used.

## 25.3 Lock Acquisition Failure

If the lock cannot be acquired within a fixed period, return an error.

The default timeout is 10 seconds.

The following option may be added in the future:

```text
--lock-timeout SECONDS
```

## 25.4 Stale Locks

The existence of the lock file alone must not be used to determine whether the house is locked.

Use the operating system’s file-locking mechanism.

An empty lock file remaining after abnormal process termination is not considered a problem.

---

# 26. Schema Versions

## 26.1 `schema_version`

Both `registry.json` and `metadata.json` contain a `schema_version`.

The initial value is 1.

## 26.2 Unknown Versions

If a newer schema version unsupported by the implementation is detected, modification operations must be rejected.

`status` or `doctor` may display any information that can be read safely, but the content must not be written back.

## 26.3 Migration

Future versions will provide explicit migration processing.

If automatic migration is implemented, a backup or another safe recovery mechanism must be provided beforehand.

---

# 27. Security and Safety

* Do not delete unmanaged paths
* Do not delete regular files or regular directories as though they were links
* Do not recursively delete a link target when deleting a link
* Before deleting an environment, verify that the target is under the house
* Only canonical paths derived from UUIDs may be used as environment deletion targets
* Do not allow `..` in relative paths stored in JSON
* Do not allow absolute managed paths in JSON to point outside the house
* Do not trust registry or metadata content alone; validate the actual file system
* Do not use names as file-system paths
* Do not output the complete environment variable set in error logs
* When executing Python, do not construct a shell command string; start the process using an argument array
* Do not overwrite an existing path at a link creation destination
* Do not treat `--force` as an option that bypasses validation

---

# 28. Error Handling

## 28.1 Error Messages

Wherever possible, errors should include:

* The operation that failed
* The target environment ID or name
* The target path
* The immediate cause
* An actionable remediation step

## 28.2 Exit Codes

```text
0   Success
1   General error
2   Command-line argument error
3   Target not found
4   Target or path already exists
5   File-system operation error
6   Management JSON read/write error
7   Consistency error
8   Permission error
9   Lock acquisition error
10  Python or venv creation error
11  Unsupported schema version
```

For `doctor`, which may detect multiple problems, exit with a nonzero status if one or more problems are found.

# 33. Final Design Decisions

This specification formally adopts the following design decisions:

1. Actual virtual environments are stored at fixed paths within the house
2. Only links are created at user-specified locations
3. Junctions are the default on Windows
4. JSON is used for management data
5. Each environment has its own `metadata.json`
6. `registry.json` is a rebuildable index
7. `metadata.json` is the authoritative source of environment information
8. JSON files are updated using atomic replacement
9. Modification operations use house-level exclusive access control
10. Deleting the last link does not delete the actual environment by default
11. The actual environment is deleted only through an explicit operation
12. The house and actual environment are never moved after creation
